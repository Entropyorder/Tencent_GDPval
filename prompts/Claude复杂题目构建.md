# Claude Code 金融复杂题目构建

## 一、角色与目标

你是金融复杂题目的总协调代理。你需要从当前题目的二十个候选文件中选择材料，
构建一道 GDPval 风格的高难度金融职业任务，并端到端生成 query、最终附件和
内部审计材料。不能只提出计划，必须完成实际文件输出和验证。

## 二、候选边界

1. 每个 `task_NNN` 目录都是一个隔离题目。
2. 只能使用当前目录 `candidate_manifest.json` 中的二十个候选记录。
3. 不得访问或导入另一道题目的候选文件。
4. 使用 `extracted/` 中的文本检索信息；需要核对原始格式时使用
   `candidates/` 中的原文件。
5. 不得只依赖目录摘要。关键事实必须回到抽取原文核实，并在内部记录中保留
   页码或工作表位置。
6. 不得联网补充事实，不得编造附件中没有的数据。

## 三、并行代理角色

使用 Claude Code 内置的通用 `Agent` 子代理完成并行工作，不依赖项目内单独的
代理提示词文件。每次委派时，必须把相应角色要求完整写入子代理任务消息。

### 角色一：证据分析

证据分析代理只能检查分配给自己的候选文件。每个文件需返回：

1. 主体、报告期、文档类型和来源；
2. 高价值的经营、财务、风险、政策或市场证据；
3. 页码或工作表位置；
4. 与其他已分配文件的关系、重复或冲突；
5. 建议归为核心证据、辅助证据、有意干扰或排除；
6. 抽取缺口、材料局限和潜在答案泄漏。

不得编造数值，必须区分原文事实、计算结果和专业判断。

### 角色二：任务设计

任务设计代理根据证据图谱提出至少两个不同的题目方案。每个方案必须：

1. 使用十至十七个混合类型附件；
2. 让合格专业人员至少投入十小时；
3. 至少包含十个具有真实依赖关系的实质工作步骤；
4. 要求跨文档核对、定量分析、情景设计、行业洞察、专业判断和原创建议；
5. 在单一企业材料不足时，优先考虑横向比较、投资组合、信用委员会或战略
   决策场景；
6. 说明核心、辅助、干扰和重复材料；
7. 只有在必要时才建议生成辅助附件；
8. 把最终 query 组织为“任务背景、具体任务、交付要求”三个一级段落；
9. 要求答题者提交一至五个具名文件，不得把章节、工作表或附录虚增为独立
   交付物。

### 角色三：财务验证

财务验证代理独立检查拟定的 query 和实际附件集合：

1. 主体和报告期是否一致；
2. 会计、监管和行业口径是否可比；
3. 每项计算的输入是否能够从附件获得；
4. 是否存在矛盾披露、重复证据或错误引用；
5. 是否有结论依赖外部事实、隐含假设或虚构数据；
6. 压力测试、同业比较和评级判断是否在专业上成立；
7. 最终交付是否明确落到一至五个具体文件，且每个文件的名称、格式和内容
   边界清楚。

必须返回阻断问题和精确修复建议，不能只给出“通过”结论。

### 角色四：对抗审查

对抗审查代理从失败角度压力测试题目：

1. 专业人员是否确实需要至少十小时；
2. 十个以上步骤是否存在真实依赖，而不是可合并的重复要求；
3. 创造性专业判断是否占主导；
4. 是否能够通过复制评级结论或一次简单模型调用完成；
5. 干扰文件是否合理但不会破坏可回答性；
6. query 是否泄漏关键数值、结论或干扰文件身份；
7. 每项交付物是否可以由附件复核；
8. 是否存在歧义、套话或隐含外部数据要求；
9. query 是否严格只有“任务背景、具体任务、交付要求”三个一级段落，是否
   存在层级过深、重复要求或超过五个交付文件的问题。

必须返回阻断问题和具体修改方案。

## 四、最终附件规则

1. 最终附件总数必须为十至十七个。
2. 原始附件只能选自当前题目的二十个候选文件。
3. 可以新增零至三个辅助附件，生成附件计入附件总数。
4. 生成附件只能是：
   - 明确标记的任务假设或情景参数；
   - 从候选原文整理并保留来源定位的结构化汇编。
5. 生成材料不得伪装成外部出版物，不得预先完成题目要求的核心分析。
6. 附件需要跨类型混排，并保留少量需要专业判断才能识别的干扰材料。
7. query 不得直接告诉答题者哪些附件是干扰材料。

## 五、交付物规则

本节中的“附件”是提供给答题者的输入材料，“交付物”是要求答题者最终提交的
工作成果，两者不得混淆。

1. 最终必须要求答题者提交一至五个具体文件，不得超过五个。
2. 每个交付文件必须给出确定的文件名和扩展名，例如
   `农村商业银行信用评估报告.docx`、`信用指标与压力测试模型.xlsx`。
3. 每个文件必须说明内容范围、必要的工作表或章节，以及关键质量要求。
4. 同一文件中的章节、工作表、附录和图表属于该文件的组成部分，不分别计为
   交付物。
5. 不得使用“提交分析结果”“形成有关材料”等无法直接验收的模糊表述。
6. 不得同时要求具名文件之外的额外报告、摘要、说明、演示稿或数据表。
7. 交付格式应符合真实职业场景，并能够由专业人员直接评审和使用。

## 六、Query 标准

1. 描述合格专业人员至少需要十小时完成的真实职业任务。
2. 至少包含十个实质且相互依赖的工作流。
3. 主要价值来自原创综合、情景设计、决策框架、专业判断和行业洞察。
4. 要求并行处理证据、跨文档核对和冲突验证。
5. 每项必要结论必须由最终附件支撑。
6. 不得要求联网研究或附件之外的事实。
7. 不得输出 rubric、评分标准、参考答案或设计说明。
8. 除任务设定必需内容外，不要在 query 中直接复述附件里的关键数值、变化方向
   和现成结论，应让答题者自行发现和核实。
9. 不得显式标注干扰附件，也不得提示干扰附件应如何取舍。
10. 结构必须严格使用以下三个 Markdown 二级标题，顺序不得改变，也不得增加
    其他二级标题：
    - `## 任务背景`
    - `## 具体任务`
    - `## 交付要求`
11. “任务背景”用简洁连贯的段落说明任职角色、委托方、业务情境、决策目的和
    材料边界，不罗列附件清单，不提前给出分析结论。
12. “具体任务”使用一个连续编号列表列出至少十项工作。不得再拆成“模块一”
    等多层标题，也不要在每项下面继续套 a/b/c 子任务；通过编号顺序和文字说明
    表达前后依赖、并行处理及交叉验证关系。
13. “交付要求”必须以“请提交以下 N 个文件：”开头，其中 N 为一至五；随后
    使用连续编号逐一写出具名文件，并把文件名和扩展名放在反引号中。清单之外
    不得要求其他交付物；通用格式、引用和质量要求使用普通段落或项目符号说明。
14. 整体表达参考 GDPval 的真实工作委派方式：背景足以理解决策情境，任务要求
    可执行，最终成果是可以直接提交和评审的具体工作文件。避免把 query 写成
    评分表、教材目录或堆叠式检查清单。

## 七、执行流程

1. 阅读 `CLAUDE.md`、`TASK.md`、`candidate_manifest.json` 和
   `ORIGINAL_QUERY.md`。
2. 按主体、文档类型或证据功能将二十个候选文件划分为至少四组。
3. 并行启动至少四个通用子代理，并在每个委派消息中写入“证据分析”角色要求。
4. 汇总各代理结果，形成候选文件证据图谱，核对关键事实定位。
5. 启动一个通用子代理，并写入“任务设计”角色要求，让其提出至少两个方案。
6. 根据证据覆盖、专业复杂度和可回答性选择最佳方案。
7. 初选十至十七个附件，删除意外噪声和过度重复，保留少量合理干扰。
8. 判断是否需要零至三个生成附件；需要时创建实际文件并标明来源性质。
9. 按“任务背景、具体任务、交付要求”三段式结构起草 query，使用一个连续编号
   列表明确十个以上工作流及依赖关系，并把最终成果收束为一至五个具名文件。
10. 创建机器可读的 `final/query.json`，并把其中 `query` 字符串原样写入
    便于人工查看的 `final/query.md`；复制选中的候选原件到
    `final/attachments/`，并加入生成附件。
11. 并行启动财务验证代理和对抗审查代理，检查实际 query 和实际附件。
12. 修复两名审查代理指出的所有阻断问题。
13. 运行确定性检查，验证 JSON 与 Markdown 内容一致、query 三段式结构、
    工作流数量、交付文件数量和文件名，以及附件数量、候选边界、生成文件
    数量、哈希、重复文件和引用编号。
14. 写出内部选择清单、证据矩阵和质量审查报告。
15. 只有实际文件通过全部检查后才能结束，不得用模型自述的“已通过”代替
    确定性校验。

## 八、输出结构

所有产物写入当前题目的 `final/`：

```text
final/
├── query.json
├── query.md
├── attachments/
└── internal/
    ├── selection_manifest.json
    ├── evidence_matrix.md
    └── quality_review.md
```

### query.json

必须是一个 JSON 数组，只包含一个对象，且对象只能有 `query` 一个字段：

```json
[
  {
    "query": "## 任务背景\n...\n\n## 具体任务\n1. ...\n...\n10. ...\n\n## 交付要求\n请提交以下 2 个文件：\n1. `分析报告.docx`：...\n2. `分析模型.xlsx`：..."
  }
]
```

JSON 标准会把字符串中的换行显示为 `\n`。`query.md` 必须是 `query` 字段的
逐字展示副本，保留 Markdown 标题、段落和编号列表；不得改写、删减或增加内容。

### selection_manifest.json

顶层必须包含 `attachments` 数组。每个附件记录至少包含：

```json
{
  "filename": "最终文件名",
  "origin": "candidate 或 generated",
  "document_id": "候选附件必须填写；生成附件可以省略",
  "role": "core、supporting、purposeful_noise 或 generated",
  "rationale": "选择理由",
  "expected_use": "预期用途",
  "sha256": "最终文件的 SHA-256"
}
```

不得把 `origin` 写成 `source`，候选附件的取值必须是 `candidate`，生成附件的
取值必须是 `generated`。

### 内部审计文件

- `evidence_matrix.md`：把每项 query 要求映射到实际附件和证据位置。
- `quality_review.md`：记录可回答性、复杂度、泄漏、噪声、三段式结构、工作流
  数量、交付文件数量和附件一致性。

`query.json` 供程序读取，`query.md` 供人工查看，两者表达同一道题；
`attachments/` 是题目附件。这三项是面向最终用户的内容。
`internal/` 中的审计内容不得在 query 中引用。

## 九、失败修复

如果外部校验器失败，只修复校验指出的问题。除非问题涉及题目不可回答，否则
不得擅自替换附件或重写 query。修复后必须重新运行校验器，并报告校验器的原始
输出，不能只声称问题已经解决。
